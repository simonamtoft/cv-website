Harness Engineering: Stop Wishing for a Better Model

By 2026 most of the engineering leverage in a coding agent sits outside the weights. This is a synthesis of where the best practitioners have landed.

Three eras, each subsuming the last

The discipline has moved through three stages. Each one contains the last rather than replacing it: a good harness still needs good context, which still needs good prompting.

Agent = Model + Harness

Everything that is not the weights - system prompt, tools, filesystem, sandbox, orchestration, hooks, guardrails, feedback loops - is harness. The empirical case is blunt: changing only the harness, on identical weights, moves the numbers materially.

52.8% → 66.5%
GPT-5.2-Codex on TerminalBench 2.0: outside the top 30 to rank 5, harness change only.
42% → 78%
Claude Opus on CORE-Bench: generic scaffold vs inside Claude Code.

The seven-lever harness

Read as a closed-loop controller around the model, a harness has seven distinct control surfaces. Each plays a different role, and each has a characteristic failure when it is missing. Click a lever to explore it.

How a harness comes to be

A harness is grown, not designed up front. The loop that produces it:

Observe the quiet repeated failure→ Minimal constraint that holds→ Verify it bites→ Discard when outgrown

A line in the harness is a fossilised failure - but with a decay term. The measure of the discipline is not how much scaffolding you have accumulated, but how much of yesterday's you managed to delete today.
