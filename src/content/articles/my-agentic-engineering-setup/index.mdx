[Agentic Engineering](/writing/agentic-engineering) sets out the principles. This companion article covers the tools and habits I use to apply them today, and it will change as harnesses and models improve.

One idea holds the setup together: a session is disposable. The plan, the decisions, the checks, and what I learn about the harness live in tickets, the repository, and the harness configuration, so the next session starts from them rather than from a transcript. The sections follow one piece of work through that setup: the ticket, the worktree it runs in, the guardrails around the agent, the context it reads, the checks before I see the result, and the slower loop that improves the harness itself.

[Pi](https://pi.dev/) is my only actively developed harness, I run most sessions through [Paseo](https://paseo.sh/), and most of my work runs through [Backlog.md](https://github.com/MrLesk/Backlog.md) tickets. Several pieces started as someone else's skill, post, or configuration that I adapted to how I work. Don't be afraid to engineer your own harness the same way: take skills and patterns you find online, change them until they fit your workflow and preferences, and publish what you build so others can do the same.

## Backlog.md tickets as the unit of work

A Backlog.md task is a Markdown file in the repository's `backlog/` folder, so it sits next to the code it describes. I triage and pick the next ready task on its terminal board or in its browser UI. Agents touch tasks only through the `backlog` CLI, never by editing the files, which keeps metadata, dependencies, and history consistent. My instructions point agents to Backlog's own guides for creating, executing, and finalizing tasks, and agents read a guide only when a turn touches tracked work.

I prefer one focused task per session, because the next session starts from the ticket anyway.

Larger efforts become several tasks with dependencies instead of one monolithic plan, and each ticket's plan is no more detailed than its work requires.

When work is too uncertain to cut into tickets yet, I sometimes use a [Wayfinder](https://github.com/simonamtoft/coding-harness/blob/main/shared/skills/wayfinder/SKILL.md) map: a parent Backlog task with child investigations that resolve important decisions one at a time. I use it selectively. Once the route is clear, conventional implementation tickets are enough.

Design decisions in a project become Backlog decisions next to its tasks, and longer reference material becomes Backlog documents.

## Isolated execution with worktrees

Independent Backlog tasks can run in separate Git worktrees. Dependent work stays sequential, which the task dependencies make explicit. [Paseo](https://paseo.sh/) creates and cleans up the worktrees, and each session in one loads the same Pi setup as a terminal session. In most of my projects the `backlog/` folder is tracked, so task updates travel with each worktree's branch and merge with the code. Where it is untracked, a setup hook in the project's `paseo.json` links every new worktree to the main checkout's tracker, so all worktrees edit the same backlog. Pi's file tools may read the other worktrees of a repository but not write to them, and on macOS the kernel command profile described below also stops shell commands from writing there. The shared `backlog/` link is the deliberate exception, and only for a command that is just a `backlog` invocation.

The aim is a backlog that stays current and keeps the important reasoning next to the code. Git makes completed work searchable, and there is no separate system to drift from the implementation.

## Operational guardrails

Before acting, the agent answers what it can from the repository and asks me when an open choice would change scope or behaviour.

Pi's sandbox works in layers, because each layer leaves a gap that the next one covers. Pi's tool-call guard checks every call before it runs, but its checks are lexical. On macOS, every shell command the agent runs therefore also executes under a kernel-enforced Seatbelt profile, and its network traffic goes through a proxy that admits an allowlist of hostnames. The same profile covers my own `!` shell commands, which keep open network access, and Paseo-driven and subagent sessions. Pi's own tools stay outside that profile, so when I need a harder boundary I run the whole process in [paseo-box](https://github.com/simonamtoft/coding-harness/blob/main/paseo/box/README.md), a container on Colima, or in confidential mode against a local model.

<Slide title="Each guardrail covers the last one's gap">

<GuardrailLayers />

</Slide>

The agent's web access takes a separate, approval-gated path rather than a gap in that proxy. Sessions started in my research vault or at the harness root get a `web_fetch` tool: I approve each exact URL, and the tool saves the page or PDF into the session workspace and returns its text as untrusted data. A `web_search` tool backed by the Brave Search API can be enabled for the same sessions, again with my approval of each exact query, but it stays off unless an API key is set, because Brave links queries to the key's account. Files I attach in Paseo are copied into the session workspace, so the agent can read them without access to Paseo's upload folder.

Some commands are allowed, but not silently. SSH and state-changing Terraform commands are often legitimate, so they ask me rather than fail. Requests that put an email address in a `User-Agent` or `From` header are denied, and a separate guard replaces the values of secret-like environment variables in tool output before it reaches the model. Git hooks also scan for secrets: the pre-commit hook fails if a known secret-token format appears in the staged additions, and a pre-push hook scans the outgoing commits again.

## Keeping the parent context lean

The parent session's context is where the agent reasons, and everything in it is sent again with every turn. Following the context-engineering principles in [Agentic Engineering](/writing/agentic-engineering), I keep it for decisions and evidence rather than raw reference material. When a session's context grows too large anyway, Pi's `/ctx-monitor` shows what is consuming it and `/skill:handoff` carries the decisions and state into a fresh session.

Large reference reads are the one thing a hook keeps out of the parent context, when the task is fact extraction rather than direct reasoning. A Pi hook blocks an unbounded read of a regular file above 16 KiB and points the parent to a shared skill. The skill dispatches a read-only `bulk-reader` subagent, pinned to a cheaper model than the parent, with the file paths and question; it returns cited findings, coverage gaps, and uncertainty in at most 600 words.

The hook only redirects; the parent still decides whether to delegate. Bounded reads of up to 350 lines remain available, as do full reads of governing instructions and native documents, and search output is outside the gate. The parent can still inspect source directly for debugging, editing, architecture, safety-critical reasoning, and decisions that need exact evidence. The threshold is based on bytes rather than lines because my measurements found bytes to be a more stable proxy for token cost across prose and code.

Whether the route saves money is a separate question from whether it works. To answer it, I ran an offline, read-only audit of my own Pi session history: 551 sessions from 2026-09-27 to 2026-11-17. It [prices every tool result](https://github.com/simonamtoft/coding-harness/blob/main/pi/agent/extensions/sandbox/README.md#session-history-discovery) from the token usage each session recorded, in two ways. Single-pass counts the tokens once, when the result first arrives. With carry re-bills the same tokens on every later turn while they stay in context; that is the cost of context build-up, and the measure I care about most. The audit runs under its own [permission grant](https://github.com/simonamtoft/coding-harness/blob/main/decisions/sandbox.md) (SBX-80) and outputs only counts, dollars, and record IDs, never prompts, file paths, or tool output.

<Slide title="Routing works per call; the money is in context">

<RoutingEvidence />

</Slide>

Observed main-agent spend over the window was $1,492, or $2.71 per session. Everything else is a modelled upper bound and is not quality-matched. Per delegation, the bulk-reader works. In total it barely moves cost: about 2.5¢ per session single-pass and 10¢ with carry, because few sessions read files large enough to route. The headline "80% saving per delegation" was true and still misleading about total cost. Delegating bulk reads is efficient per call, but its total value is capped by how often large reads happen, so I should have measured that addressable pool before tuning the gate. September's controlled comparison, which cut parent-context tokens by 95.8–95.9% per delegation, measured the same per-call effect. The [summary table](https://github.com/simonamtoft/coding-harness/blob/main/pi/agent/extensions/read-routing/README.md#current-evidence) has the total-cost shares.

Re-reading afterwards is not the problem. In recent work the agent re-read worker-covered files in 6 of 67 runs, costing under 2% of the saving and never turning a run into a loss. In September, during deliberate routing trials, re-reads made 5 of 72 delegations worse than reading directly. Redundant dispatch costs more: 19 of 67 recent worker runs read nothing the session didn't already have. Pushing delegation harder wouldn't help either. Forcing a worker call after every blocked read adds at most about 1¢ per session, or 0.4 points of total cost, and in nearly half of those cases the agent later edited the file, so it needed the source anyway. I have kept the routing unchanged (SUB-33 in the [subagent decisions](https://github.com/simonamtoft/coding-harness/blob/main/decisions/subagents.md)).

The real cost is carried context. Of the $601 that tool results in context cost, $489 was carrying them through later turns, 4.4 times their first ingestion; single-pass accounting understates context costs about fourfold, so I now report savings both ways, carry first (SUB-34). Most of that carry comes from many small search, `cat`/`sed`, and paged-read results that no file-size gate sees, each too small to be worth a worker call. Cache rewrites are the second large cost, mostly after idle gaps of more than five minutes, when the prompt cache had expired. The audit also corrected two of my assumptions: text in these sessions averaged about 2.6 characters per token, not the 3.6 I'd assumed, and on Opus 5.5 a cache read costs 1/20 of the uncached input rate, not 1/10.

The biggest untested lever is dropping old tool results at the moment the cache must be rewritten anyway. Its modelled ceiling is $0.31–0.55 per session, depending on whether results older than 40 or 10 turns are dropped. Only 0.9% of dropped results were re-read later, but that is a lower bound on what the agent still needed, not proof that quality holds. So the next step is a quality-matched A/B test of clearing stale results. It passes only if task pass rate is unchanged, combined cost including re-reads falls at least 10%, and cleared content is re-read in fewer than one task in five. The [full tables and re-read analysis](https://github.com/simonamtoft/coding-harness/blob/main/pi/agent/extensions/read-routing/EVIDENCE.md#context-carry-audit-2026-11-17) are in the harness repository.

The process lesson is the one I would pass on: a reproducible, privacy-preserving audit beat my intuition about where the money went. Spotify's roughly 90% figure motivated the pattern; I do not claim it for this setup.

## Feedback loops

Two loops run inside each task and keep the agent's work honest before I read the result, which is usually a local commit rather than an uncommitted diff.

<Slide title="Checks run before I read the commit">

<FeedbackLoops />

</Slide>

Verification runs automatically. Pi's `verify-turn` extension looks for the project's `.agent/verify.sh`, or a `verify` task in a Taskfile, and runs it after any model run that changed project content. Read-only, commit-only, Markdown-only, and edit-then-commit runs skip it, but a change that mixes Markdown and code is still verified. While it works, the agent runs only narrow checks and leaves the full suite to this loop. Because the verifier is repository code the agent can edit, a changed verifier is first read by a separate reviewer agent and runs only if that reviewer clears it. Once a run passes verification with no deferred review pending, or a later run needs no verification (a Markdown-only edit, say), `verify-turn` runs the `quick-commit` skill on the files that the session's own edit and write tools changed. It asks first if the commit plan has warnings and does not offer the same unchanged files a second time. It never commits changes made through shell commands, by subagents, by me, or by other sessions, and it never pushes; `git reset --soft HEAD~<n>` undoes the last n commits.

Review is proportional to risk. A correctness reviewer checks changes to persistence, public APIs, lifecycle behaviour, or anything spanning modules, and a security reviewer joins only for security-relevant changes. Before a security review, the reviewer receives the established guards from earlier security fixes that match the change, recorded in `SECURITY_CONTEXT.md`, so it can check that the change does not weaken them. Each review starts from a stated intent (the requested outcome and its acceptance criteria), not from the diff alone. Reviewers must also say what they covered. The reviewers, like the other subagent roles, are short definitions in [`pi/agent/agents/`](https://github.com/simonamtoft/coding-harness/tree/main/pi/agent/agents), each owned by one skill or extension. Their transcripts land in the session workspace, so I can follow a run while it works.

## Improving the harness

The harness itself improves on a slower cycle with two inputs. The first is self-reporting: when the sandbox, an instruction, a skill, or a tool gets in the way, the agent calls `report_papercut`, which appends the friction to an untracked `PAPERCUTS.md` in the harness checkout from any project's session. I review that file periodically and turn recurring entries into a Backlog task that fixes the harness, a decision-ledger entry that records why not, or a tool reminder that steers agents until the fix lands.

</Slide>

The second input is mine: friction I run into myself, and skills, tools, and patterns I come across on Hacker News, LinkedIn, from colleagues, and in other people's setups. These go through the same review rather than straight into the setup. Spotify's Portal post shaped the bulk-read route, and the `analyze-sessions` query scripts are adapted from another engineer's Pi configuration. Others I turn down, and the ledger records why.

The [decision ledger](https://github.com/simonamtoft/coding-harness/blob/main/DECISIONS.md) holds what the code cannot explain: one file per area, where each entry records what was refused, why, and when to revisit it. Agents read the area they touch before proposing a change. This stops them from re-proposing approaches I have already rejected, such as the output-compression rules from Caveman that I turned down after review and measurement.

[`tool-reminders`](https://github.com/simonamtoft/coding-harness/tree/main/pi/agent/extensions/tool-reminders) covers the time between a reviewed papercut and its fix. It refuses the first matching tool call in a session with a reminder as the reason, and the retried call runs. Each rule cites the papercuts behind it and names the change that retires it. Terraform was an early case: provider plugins could not start inside the command sandbox, so `validate` and `plan` failed, and a rule backed by four papercuts told agents to hand those commands to me. The cause, a session temp path too long for the plugins' Unix sockets, had six papercuts behind it. Once [SBX-62](https://github.com/simonamtoft/coding-harness/blob/main/decisions/sandbox.md) shortened the path, I deleted the rule.

I added and removed pieces of the harness in response to observed failures like these. Papercuts capture the friction an agent notices; for the rest, I run retrospectives on finished sessions with the `analyze-sessions` skill and usage audits over session history, such as the read-routing audit above.

## One setup across harnesses

My [coding harness](https://github.com/simonamtoft/coding-harness) is public and splits into a shared layer and per-harness parts. The shared layer contains user-authored resources any harness can use: `AGENTS.md`, skills, and command-safety and read-routing regression contracts. Pi keeps its own extensions, prompts, and agents. Claude Code's hooks, settings, and agents are still there, but I parked that harness in November 2026. Its files stay linked and their tests still run, but new work goes into Pi only, so Claude Code lacks Pi's newer protections such as kernel command confinement. Credentials, sessions, caches, provider configuration, and generated state remain local.

A link script installs the shared resources without maintaining copies and links Paseo's daemon configuration. Its optional package step installs the Pi packages listed in the version-controlled manifest, currently just `pi-status-footer`. When a commit touches Pi runtime inputs (shared `AGENTS.md` or skills, Pi agents, extensions, prompts, MCP config, or the package manifest), a pre-commit hook starts Pi without a model call to check that every extension, skill, and prompt still loads from the checkout. Local Pi settings record what is installed on a given machine. Keeping the shared layer small means another harness can join later without moving its source of truth.

Skills follow the same rule: each answers one question and arrives when a gap shows up. Recent additions include `threat-model`, `check-packages` for registry and advisory lookups before adding a dependency, `ui-design`, `record-decision`, `zoom-out` for reframing an approach before committing to it, and `cleanse` for tidying a repository before handover. Not every experiment earns a place in daily use. `local-models/` holds playgrounds for small local models such as Bonsai and Gemma, and a paid evaluation suite for instruction changes is parked until its results are reliable enough to act on.

## Build your own

Most of this setup grew piece by piece, in response to failures I hit and friction agents reported, and the details will keep changing faster than this article. The idea from the start stays the same: keep what matters in tickets, the repository, and the harness, so any session can pick it up. If you build your own harness, start from what others have published, bend it to your workflow, and make yours public too. Mine is in [coding-harness](https://github.com/simonamtoft/coding-harness), and its decision ledger records what I tried and turned down.
