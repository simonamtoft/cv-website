The first reaction when a coding agent disappoints is usually to wait for a better model. The model still matters, of course, but much of the leverage now sits outside its weights. It sits in the context you give it and the machinery wrapped around it. Those are the parts you can change yourself. Prompt engineering did not disappear so much as get folded into two broader disciplines: context engineering and harness engineering. Together, I think of them as agentic engineering.

## The workflow underneath

Both disciplines support the same way of working. Strong practitioners do not point an agent at a large task and watch it type. They spend time on the plan, usually through several rounds with the model, then divide the work into small pieces and verify each checkpoint.

> Nearly everything that makes a software engineer better at the job makes an AI agent better too.

This is not tied to one vendor. GitHub recommends roughly the same sequence: prototype cheaply, plan carefully, let a loop run to completion, then review the result. The same discipline applies further upstream as the work gets larger.

For work that will outlive a single session, I sometimes use a [wayfinder](https://github.com/simonamtoft/claude-code-setup/blob/main/skills/wayfinder/SKILL.md) map: a shared board of decision tickets that settles the consequential *what* and *why* before implementation starts. I like the idea more than I like treating the full workflow as a default. Combined with `grill-me` or other planning skills, it can turn each answer into another branch of questions and make planning a rabbit hole. I now use it selectively, stop once the important decisions are clear, and prefer a short plan when that is enough.

For larger multi-session efforts, I currently use [Backlog.md](https://github.com/MrLesk/Backlog.md), and it has substantially improved both the feel and the UX of working with agents. Instead of using plan mode to produce one monolithic implementation plan, I use it to design and refine the tickets. The agent can then work through those durable units one at a time, while decisions, progress, and dependencies remain visible across sessions. [Fiberplane](https://fp.dev/) explores a similar CLI-native model.

The useful principle is not to maximise the number of tickets. It is to keep the backlog alive and the consequential reasoning close to the code, where Git makes completed work searchable without introducing another system that can drift away from the implementation.

The loop becomes useful when the agent can check its own work. Tests, linters, and type-checkers separate a plausible change from a verified one. This is probably the highest-return capability you can give an agent.

One small habit helps too: keep the model and reasoning level fixed across a feature. That lets the prompt cache keep paying off instead of resetting with every turn. Context engineering decides what the agent knows while it plans and works. Harness engineering provides the loop, the checks, and the boundaries that pull it back when it goes astray.

## Context engineering

If the model is a processor, context is its working set. It remembers nothing between turns unless that information is placed in the current window. Context engineering is the work of deciding what enters that window, in which order, and when to discard it.

<Slide title="The forgetful senior">

> Imagine the best software engineer in the world, who wakes up each morning having
> forgotten every architectural decision and every line of code from the day before.
> Would you hire them?

</Slide>

Errors get more expensive the further upstream they occur. A bad line of code may cost one line. A bad plan can send the whole task towards the wrong solution. Faulty research means the plan rests on a misunderstanding; a faulty specification means the team is solving the wrong problem. Worst of all is a bad instruction in a context file that steers every session, potentially for every engineer in the organisation.

<Slide title="The hierarchy of leverage">

<LeveragePyramid />

</Slide>

The result is a quality ceiling: research limits the plan, and the plan limits the implementation. Careful coding cannot rescue a misunderstood problem. I would rather spend human attention on the research, specification, and shared context than on polishing code the agent was always happy to generate.

All of that material competes for space in working memory: system instructions you do not control, tool descriptions loaded at startup, context files you wrote, memories the agent saved, and the running transcript of the task. You can shape only part of it, but all of it consumes the same fixed budget. The job is to spend that budget deliberately.

<Slide title="The context window">

<ContextWindow />

</Slide>

As the window fills, reliability tends to fall. The model's own earlier output is especially costly because errors and stale assumptions remain in view. A larger context window does not remove this problem; it gives you a larger haystack. Isolation matters more than raw capacity.

A useful rhythm follows: *expand to plan, then reset to execute*. Let the context grow while gathering the material needed for research and planning. Once the plan is sound, begin implementation in a clean window with only that plan and the necessary project context.

<Slide title="Expand to plan, then reset to execute">

<ContextFlow />

</Slide>

Verification should respect the same attention budget. A passing check can stay silent. A failing check should return the relevant error and wake the agent back up. Thousands of lines of successful test output only bury the task.

There is a security consequence here. A poisoned `AGENTS.md` is both a high-leverage context artifact and an attack surface. The same instruction can steer many sessions, so the machinery around the model has to constrain what those instructions are able to cause.

## Harness engineering

The harness is everything around the model. The weights are one fixed component inside a larger system.

<AgentAnatomy />

How much of that system you control depends on the provider. Claude Code keeps its system prompt, core tools, and sub-agent implementation out of reach. It exposes configuration such as permissions, MCP tools, and sandbox settings, while leaving you to author `CLAUDE.md`, hooks, skills, tests, and linters. Pi makes a different trade. It deliberately omits MCP, sub-agents, and permission prompts, which leaves more of the system prompt, orchestration, and guardrails for you to build.

So "engineer the harness" does not mean the same thing in every tool. The first consequential choice is the harness itself because that choice determines which other parts you can touch.

This is not just a naming exercise. In one TerminalBench run, changing the harness moved a fixed model from roughly 33rd place into the top five. Many disappointing runs are configuration failures rather than model failures. Waiting for the next release is often less useful than fixing the system around the model you already have.

GitHub makes the same argument from outside the Claude and LangChain ecosystem. It calls Copilot "an agent harness" and titled its own account *the harness is all you need (mostly)*. The parenthesis is important. Learning the harness you already use will usually beat chasing each new model, but skills, MCP servers, and custom agents become useful as workflows grow. Plenty of published harness advice is still slop.

A harness is concrete, not an abstract layer in a diagram. The reason for each component becomes clearer if you start with what a raw model cannot do.

A model is text in, text out, with no persistent state. Give it a filesystem and Git and it gets a workspace, a place to offload context, memory across sessions, and version history. It can emit text but cannot act, so give it tools, especially bash and code execution. It can then write a small tool when needed instead of waiting for somebody else to provide one. This also suggests a boundary: when the work is deterministic, ask the model to write or invoke an inspectable, testable program rather than produce the answer probabilistically.

Arbitrary code execution is unsafe on a bare machine. Put it in a sandbox stocked with the things it needs to observe its own work: test runners, a browser, logs, and screenshots. The model's training knowledge is frozen, so give it memory files and search. Its reasoning is serial and confined to one window, so let it delegate isolated investigations to sub-agents with fresh windows and separate Git worktrees. That keeps messy exploration out of the main context and allows independent work to run in parallel. The filesystem and Git come first; most of the other capabilities depend on them.

<Primitives />

</Slide>

A component should earn its place. If you cannot name the behaviour it exists to produce, leave it out.

Once the substrate is in place, the remaining question is how to steer the work running on it. Control theory offers a useful vocabulary. Guides act before the agent does something; sensors observe after it acts. In control terms, those are feedforward and feedback. Sensors alone correct mistakes but force each new session to rediscover them. Guides alone encode rules without checking whether those rules worked. A complete loop needs both. Across that loop, I find seven useful control surfaces, each tied to a particular kind of failure.

<Slide title="Harness seen as a control loop">

<HarnessController />

</Slide>

The seven controls fall into functional groups. Guides and Exemplars steer before action. Mirrors expose the agent's state before a tool call, while Sensors inspect the result afterwards. Rails and Throttles limit damage. Scaffolds divide work so a long task does not decay inside one overloaded window.

Do not try to design the whole harness up front. Grow it from observed failures. When the agent makes a repeatable mistake, add the smallest constraint that prevents it: a line in `CLAUDE.md` before a hook, and a hook before a hard deny rule. Stronger controls are harder to unwind. Each corrective rule should point back to something that actually went wrong. Ratchet from evidence instead of brainstorming imaginary failures. Configuration is often much shorter than the prose used to explain it:

```json
{
  "permissions": {
    "deny": ["Bash(rm -rf *)", "Bash(git push --force*)"]
  },
  "hooks": {
    "PostToolUse": [{ "matcher": "Edit", "command": "npm run lint --silent" }]
  }
}
```

Not every instruction comes from a failure. Some encode personal working preferences: how much explanation you want, when the agent should pause, or how much it may change before asking. The ratchet protects correctness. These preferences make the tool fit the person using it.

Scaffolds deserve a closer look because this is where teams tend to systematise their working methods. In practice, a scaffold is often a *skill*. A skill is a folder rather than a single file: a short entry point beside scripts, references, and templates that load only when needed. The description triggers it, so the full material does not consume context in every session.

Two authoring habits matter. Give the agent scripts to run instead of repeatedly describing mechanical steps in prose. That prevents it from rebuilding the same boilerplate and keeps its attention on the decision at hand. Keep a gotchas section too, and add to it when a recurring mistake appears. It is the same ratchet, stored inside the scaffold.

Rails contain the OS-level security model and answer the poisoned-`AGENTS.md` problem. A coding agent usually inherits the permissions of the person who launched it. Cloud credentials, SSH keys, and registry tokens may all be one command away. The main threat is indirect prompt injection: hostile instructions arriving through a repository, pull request, dependency, or context file. An application can inspect a tool call before execution, but it loses visibility once an approved subprocess starts. A restricted capability may still be reached through an apparently safe command.

The hard boundary therefore belongs below the application. A sandbox is not advice about which commands to avoid. It is a limit the process cannot negotiate with: writes confined to the project and a scratch directory, network access denied by default, and individual hosts approved when needed. The operating system enforces those rules across subprocesses. Command-string matching cannot provide the same guarantee.

I use the two layers for different jobs. The sandbox controls what the agent *can* do. Application rules judge what it *means* to do. Deny rules and pre-tool hooks remain useful for destructive actions inside the boundary whose intent is visible, such as force-pushing, rewriting history, or staging a secret.

Read access remains an important gap. [Claude Code's sandbox](https://code.claude.com/docs/en/sandboxing#configure-sandboxing) confines writes and network access by default, but sandboxed commands can still read much of the disk, including `~/.aws` and `~/.ssh`. There is no built-in credential list, so explicit denies like these do real work:

```json
{
  "sandbox": {
    "enabled": true,
    "excludedCommands": ["gh", "terraform", "gcloud"],
    "credentials": {
      "files": [
        { "path": "~/.aws", "mode": "deny" },
        { "path": "~/.gnupg", "mode": "deny" },
        { "path": "~/Library/Keychains", "mode": "deny" },
        { "path": "~/.npmrc", "mode": "deny" }
      ]
    }
  }
}
```

A boundary that blocks legitimate work will eventually be disabled, so escape hatches matter. Some tools really do fail under confinement. Go-based CLIs, for example, can fail TLS verification under macOS Seatbelt; that is what the named `excludedCommands` above are for. A specific exemption is better than switching off the sandbox. Other sandbox-related failures should be retried only after explicit approval. Each exception is still a hole in the boundary, not a box to click through without thinking.

That same boundary enables the fast path. An agent can run in allow-all, approve-nothing mode inside a sandbox. It should never run that way on a bare machine.

<Slide title="The discipline">

> A line in the harness is a fossilised failure, but with a decay term. The
> measure of the discipline is not how much scaffolding you have accumulated, but
> how much of yesterday's you managed to delete today.

</Slide>

Deletion is the neglected part of harness engineering. As models improve, old scaffolding becomes drag. A constraint that once prevented failure may later obstruct a more capable model. Make this a routine audit instead of waiting until the setup feels unbearable. Claude Code's `/checkup` command looks for this kind of rot: unused skills, slow hooks, and an overgrown `CLAUDE.md`. You can also write your own pruning skill.

My [Claude Code setup](https://github.com/simonamtoft/claude-code-setup) is public as a worked example. Its context files, hooks, and skills were added and removed in response to the failure modes described here. Because they are plain files, I symlink the same artifacts into other harnesses such as [Pi](https://pi.dev/) instead of maintaining two copies.

Better models do not eliminate harnesses. They change them. Old constraints disappear, and harder tasks reveal new failures.

### Two teams who ran it to the limit

At OpenAI, a team shipped an internal product of roughly a million lines with *no manually-written code*. Around 1,500 pull requests went through a process in which humans steered and agents executed. Repository knowledge was the system of record. A single enormous context file had failed for the usual reason: when everything is important, nothing is. The team replaced it with a hundred-line `AGENTS.md` that acted as a table of contents for a structured `docs/` directory.

They enforced architecture through invariants rather than prescribed implementations. Custom linters returned errors that included the fix. Background agents scanned the repository, graded drift, and opened refactoring pull requests. This is what Rails, Sensors, and Guides look like at organisation scale.

Anthropic's long-running application experiments expose a different quality problem: agents are generous when grading their own work. A common failure is for an agent to reread its implementation, declare it good enough, and stop. Anthropic split the harness into a planner, generator, and skeptical evaluator. Tuning a standalone critic is easier than teaching the generator to distrust itself. The experiment also demonstrates why old scaffolding should be discarded. Controls needed for one model were removed when the next model no longer needed them.

This pattern is already moving from lab setup to product feature. GitHub Copilot includes a "rubber duck" review in which a model from a different family checks the generator's work. Different training data may leave different blind spots. The loop continues until both models agree that only low-value nits remain. The doer and judge are separate, without requiring users to build a custom harness.

<Slide title="Separate the doer from the judge">

> Agents grade their own work generously. The most common autonomy failure is an
> agent re-reading its own code, calling it fine, and stopping. Tuning a skeptical
> evaluator is more tractable than teaching a generator to distrust itself.

</Slide>

## Scaling beyond one developer

So far this is a single-player setup: one engineer, one agent, one repository. Most of these practices work well at that scale. The unsolved problem is multiplayer, where several engineers each run several agents against the same codebase.

The engineer's role changes first. When the agent writes most of the code, the human spends less time typing and more time directing. They state the goal, constraints, and acceptance criteria, then judge the result. Choosing what to build and deciding whether it is correct become the scarce skills. The bottleneck moves from writing to review.

That shift is already visible. In 2026, Anthropic reported that Claude authored more than 80% of its merged code and that the typical engineer merged about eight times as much code per day as two years earlier. Human engineers directed and reviewed rather than writing most of it. By Amdahl's law, that extra throughput lands on the remaining manual step. Anthropic's response was to automate part of review with a Claude reviewer that runs before merge.

<Slide title="The bottleneck moves, it does not vanish">

> Throughput is up, but what survives? When agents write most of the code, human
> review stops being one step among many and becomes the rate-limiter for the
> whole system.

</Slide>

The gains do not land this cleanly everywhere. Faros AI's 2026 telemetry covers 22,000 developers. It found more throughput alongside faster growth in bugs, incidents, and rework: bugs per developer rose by half, production incidents increased several-fold, code churn grew nearly tenfold, and roughly a third more pull requests merged without any review. Faros calls this *Acceleration Whiplash*: systems built for human-paced work receiving more output than they can absorb.

These reports are not necessarily in conflict. Anthropic describes a heavily scaffolded environment with an automated reviewer. Faros measures average codebases, where many more pull requests now skip review. The harness explains much of the difference. AI-generated code often looks convincing. It is idiomatic and well named, while the logical flaw is easy to miss. Sensors, Mirrors, and human review are not ceremonial overhead. Without them, higher throughput can simply produce a larger mess.

Humans also need to review at a different altitude. Line-by-line inspection offers less value when the machine reliably produces tidy code. The larger risk is whether a collection of changes fits together, especially at integration points. The agent should submit two things with the code: evidence of what it verified and a clear account of how the change fits the existing system. Review the seams, not every line.

This is why I am less interested in waiting for the next model than I used to be. I cannot change its weights. I can change what it sees, what it may do, and what evidence it must produce before I trust the result. That is the part worth engineering.
